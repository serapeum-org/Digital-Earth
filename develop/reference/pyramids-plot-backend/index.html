    digitalearth as a pyramids plot backend#

    pyramids renders through cleopatra (matplotlib) by default. Ask any pyramids object for another backend and it looks for a registered renderer:

    from pyramids.dataset import Dataset

ds = Dataset.read_file("examples/data/acc4000.tif")

ds.plot()                        # matplotlib, through cleopatra — pyramids' own path
ds.plot(backend="interactive")   # a digitalearth InteractiveMap
ds.plot(backend="3d")            # a digitalearth Scene3D
ds.plot(backend="web")           # a digitalearth WebMap

    digitalearth registers itself for those three names in the pyramids.plot_backends entry-point group, so pyramids discovers it rather than importing it by name. The dependency stays one-way — digitalearth depends on pyramids-core; pyramids never names digitalearth in its own code.

    # digitalearth's pyproject.toml
[project.entry-points."pyramids.plot_backends"]
interactive = "digitalearth.pyramids_backend:interactive"
"3d" = "digitalearth.pyramids_backend:three_d"
web = "digitalearth.pyramids_backend:web"

    You do not install anything extra for this

    A registered entry point simply wins over the fallback pyramids keeps for a plain digitalearth install. The difference is what happens to the arguments — see below.

    Why an adapter, and not just quickmap#

    pyramids forwards the data-selection arguments of the call it was given, in its own vocabulary. Three of those names mean something different here, so they are translated on the way in. Everything else passes through untouched.

    pyramids forwards digitalearth takes Why
    band=0 (0-based) band=1 (1-based) 0-based upstream, 1-based here. Unshifted,
    band=0 read as index -1.
    variable_name= variable= The UgridDataset facade's spelling of
    the mesh selector.
    interval=200 (ms/frame) fps=5.0 The facades describe an interval; the
    tier verbs take a rate.

    title, basemap, a bool colorbar, kind, cmap, column and variable need no translation and are forwarded as they arrive.

    What is refused, and why it is not ignored#

    pyramids drops defaulted arguments before forwarding, so anything that arrives was set deliberately. An argument this seam cannot honour is therefore refused by name rather than dropped — a silently-ignored argument is indistinguishable from an applied one.

    Refused Do this instead
    exclude_value digitalearth applies its own nodata handling; mask upstream, or plot on backend="matplotlib".
    rgb_options Build the composite with Map.rgb_composite on the static tier.
    selectors, axes Choose a NetCDF slice with variable= and band=.
    bands, animation_axis_values, interval
    on a still plot    		 Call animate(backend=…) instead.

    The matplotlib-only styling (the typed color / contour / cells / data_style / classify groups, the points overlay and a ColorBar instance) never reaches here at all — pyramids rejects those before dispatch.

    Animation#

    Dataset.animate(backend=…) and friends forward animate=True. Two of the three tiers can serve it:

    from pyramids.dataset.collection import DatasetCollection

stack = DatasetCollection.from_files(["examples/data/acc4000.tif"] * 3)

stack.animate(backend="interactive", interval=200)                     # a Panel player
stack.animate(backend="interactive", interval=200, path="flood.gif")   # written to a file
stack.animate(backend="web", interval=200, path="flood.gif")           # written to a file
    • interactive builds a time cube and returns a Panel player, or writes a GIF/MP4 when you pass a path.
    • web animates only to a file, so path= is required; without one the call is refused by name.
    • 3-D is refused by name. Its Scene3D.record needs a caller-supplied update callable and Scene3D.orbit sweeps the camera over a static scene, so neither can be driven from a plot call's keywords. Build the scene with digitalearth and call one of them directly.

    Checking what is registered#

    from pyramids.base._plot_backends import plot_backends, resolve_plot_backend

sorted(plot_backends())            # ['3d', 'interactive', 'web']
resolve_plot_backend("interactive")  # digitalearth.pyramids_backend:interactive

    Needs a pyramids-core that ships the seam

    The pyramids.plot_backends group is resolved by pyramids-core's plot-backend seam. Until a pyramids-core release carries it, the entry points are registered but nothing reads them, and plot(backend=…) behaves as it did before. Nothing breaks in the meantime — the registration is inert, not conflicting.

    digitalearth.pyramids_backend #

    Serve pyramids' plot(backend=…) seam from digitalearth's three non-matplotlib tiers.

    pyramids-core resolves a non-matplotlib backend= through the pyramids.plot_backends entry-point group: Dataset.plot(backend="3d"), NetCDF.plot(backend="interactive") and the rest hand the object to whichever callable is registered under that name. This module is the registered end of that seam — one callable per tier, each matching the contract shape fn(obj, *, backend, **kwargs).

    Registering it is not merely cosmetic. Without an entry point pyramids falls back to importing digitalearth by name and calling quickmap directly, which forwards its own vocabulary verbatim; three of those keywords then reach cleopatra and are refused in cleopatra's words, naming cleopatra's allowlist to someone who only ever wrote ds.plot(backend="web"). The adapter exists to translate between the two vocabularies, and to refuse what digitalearth cannot honour by name rather than leaking a lower layer's complaint or silently dropping the argument.

    Three translations are genuinely necessary, because the facade and this package count and spell things differently:

    • band is 0-based upstream and 1-based here. pyramids documents the forwarded selector as "a 0-based raster band index (band 0 is the first band, not band 1)", while digitalearth's public band= is 1-based everywhere. Forwarded unchanged, band=0 reached the reader as index -1 and raised band -1 is out of range for a 1-band dataset — the off-by-one reported in #501.
    • variable_name is this package's variable. The UgridDataset facade spells the mesh selector variable_name; quickmap spells it variable.
    • interval is milliseconds; the tiers take fps. The animation facades forward a frame interval, and every digitalearth animation verb takes a rate instead.

    The module import is deliberately light — standard library only. Discovery imports every registered entry point, so a heavy import here would pull a drawing stack into a bare import pyramids; quickmap and the tier classes are imported inside the callables.

    """Render a pyramids object on the HoloViz tier, for ``plot(backend="interactive")``.

        An :class:`~digitalearth.interactive.InteractiveMap`, or — for an animation call — its

          engine is imported, and says where the capability does live:
            ```python
            >>> from digitalearth.pyramids_backend import interactive
            >>> try:
            ...     interactive("a-dataset", backend="interactive", rgb_options={})
            ... except ValueError as exc:
            ...     print(str(exc).split(": ")[1].split(". Drop")[0])
            a three-band composite is built with Map.rgb_composite on the static tier, which this seam does not reach

            ```

            ...     print(str(exc).split(". ")[0])

        three_d: The same seam on the PyVista tier.
        web: The same seam on the MapLibre tier.
